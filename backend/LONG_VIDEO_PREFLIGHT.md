# 실제 영상 확보 후 분석 실행 절차

현재 버전은 업로드·등록·조건부 추정 인터페이스를 갖췄지만, **30~60분 밀집 영상의 FULL 분석/저장/리플레이까지 무조건 처리 가능한 상태는 아니다.**
아래 크기·행 수·메모리·코덱 조건을 먼저 확인한다. 이번 점검에서는 기존 AI/Worker/환경을 수정하지 않았다.

## 1. 촬영·파일 전달

장소 이름/유형/주소와 평면도, 카메라 ID·위치·방향·관측 범위·중복 시야, 관측 구역과 예측 대상 구역을 기록한다.
행사 여부/단계·조명·환경과 실제 촬영 날짜를 기록하며 모르면 미확인으로 둔다.
원본 파일 이름·SHA-256·코덱·해상도·FPS·프레임 수·길이·파일 크기·촬영 시작/종료 시각을 함께 전달한다.
파일 수정 시각이나 업로드 시각을 촬영 시각으로 쓰지 않는다. MP4라도 브라우저에서 디코딩되지 않을 수 있다.

현재 Chrome에서 기존 짧은 원본은 재생됐고, 이번 합성 MP4의 mp4v 코덱은 재생되지 않았다.
촬영 장비의 실제 MP4를 미리 가져와 원본 재생·중간/끝 탐색을 시험한다. 브라우저 호환 H.264 계열을 우선 확인한다.
원본은 보존한다. 코덱 변환이 필요하면 별도 사본과 변환 이력을 관리하고 기존 파일을 덮어쓰지 않는다.

Tracker는 프레임 순서와 `i/fps`로 시각을 만든다. VFR, 원본 프레임 누락, 장시간 시계 드리프트를 자동 보정하지 않는다.
가능하면 일정 FPS의 원본을 확보하고 여러 카메라의 공통 사건을 시작/끝에서 대조한다.
카메라별 시간 오프셋과 근거를 기록하고 확인된 자료만 동기화로 지정한다. 한 개 상수 오프셋으로 드리프트가 해결됐다고 가정하지 않는다.

## 2. 파일 크기와 디스크

| 경로 | 파일당 한도 |
|---|---:|
| 기존 `/api/videos/upload` | 200MiB = 209,715,200 bytes |
| `/sessions` 신규 raw upload | 기본 2GiB = 2,147,483,648 bytes |
| 신규 경로 설정 상한 | 8GiB = 8,589,934,592 bytes |

`CAPTURE_MAX_UPLOAD_BYTES`는 API 시작 시 읽고 8GiB로 상한 제한한다. 이번 점검에서 설정을 바꾸지 않았다.
저장 공간 1GiB reserve는 업로드 guard일 뿐, 분석 산출물/재시도/백업에 충분하다는 의미가 아니다.
프런트 업로드 요청 제한은 30분이다. 프록시의 body/timeout 제한은 별도 배포 설정을 확인한다.
업로드 길이에 30분/1시간 제한은 없지만 파일 크기 제한은 그대로 적용된다.

원본 크기(GB, decimal) = bitrate(Mbps) × 초 / 8000.

| bitrate | 30분 | 1시간 |
|---|---:|---:|
| 4Mbps | 0.9GB | 1.8GB |
| 8Mbps | 1.8GB | 3.6GB |
| 16Mbps | 3.6GB | 7.2GB |

따라서 8Mbps·1시간 원본은 기본 2GiB에 들어가지 않는다. 정책 변경이나 별도 파일 준비를 담당자가 결정해야 한다.
업로드와 분석의 처리 시간은 별개이다. 느린 회선에서는 크기 한도보다 먼저 업로드 timeout에 걸릴 수 있다.

분석 중 tracker CSV·프레임 인덱스, 5개 결과 CSV, sidecar JSON과 로그가 생긴다.
성공 결과 CSV는 staging과 별도 immutable 보관 사본을 갖는다. 실패/재시도마다 별도 산출물이 쌓일 수 있다.
현재 tracker 경로는 상시 annotated MP4를 생성하지 않고 원본+브라우저 오버레이를 사용한다.
별도 분석 영상 저장을 예상 용량에 자동으로 더하지 않는다. 향후 렌더링하면 그 bitrate만큼 추가해야 한다.

## 3. 장시간 데이터 상한을 먼저 계산

검출 행 수 ≈ FPS × 영상 초 × 프레임당 평균 검출 수. ID가 없는 박스도 tracking 행에 포함된다.

| 제한 | 현행 값 | 근거 |
|---|---:|---|
| 리플레이/탐지 view | tracking 500,000행 | `detection_view.read_frames` |
| 리플레이 입력 | tracking 64MiB, 영상 500,000프레임 | `detection_view.for_job`, `replay_view.cached` |
| 리플레이 프레임 인덱스 | 32MiB | `replay_view.cached` |
| 결과 CSV 파일별 | 64MiB | `vision_csv.MAX_FILE_BYTES` |
| 개인 방향 CSV | 1,000,000행 | `vision_csv.validate_bundle` |
| 기타 결과 CSV | 종류별 100,000행 | 같은 함수 |
| 학습 export | 250,000행/16Mi 문자 | `capture_sessions.export_dataset` |

25fps에서 30분 평균 12개 박스 또는 1시간 평균 6개 박스면 tracking 50만 행을 넘는다.
1시간 평균 12명 수준이면 개인 방향 100만 행을 넘을 수 있다. 실제 행 수는 유효 ID/초기화/검출 조건에 따라 다르다.
구역별 초 통계는 1시간×28개 구역이면 100,800행으로 종류별 10만 행을 넘을 수 있다.
분석은 진행됐어도 마지막 결과 import에서 실패하거나, DB 집계가 있어도 리플레이/조건부 추정이 불가능할 수 있다.
단순히 업로드 성공을 전체 분석 성공으로 판단하지 않는다.

전체 CSV를 여러 번 DataFrame으로 읽고 병합하며, 전환 요약과 리플레이도 프레임/박스를 메모리에 모은다.
이 부분은 bounded streaming 처리라고 볼 수 없다. 긴 영상·많은 인원일수록 RAM 위험이 커진다.
단순히 상한 숫자만 높여 해결하지 않는다. 메모리/리플레이 전송/저장 정책의 별도 보완이 필요하다.

분할 운영을 선택하면 원본을 보존하고 시작 offset·촬영 시각·원본 recording group을 남긴다.
한 카메라의 활성 파일 하나라는 현재 세션 제약과 모델 최소 이력, 추적 ID 초기화, 구간 경계의 누락을 함께 고려한다.
원본을 잘랐다는 이유로 독립 학습 샘플로 취급하거나 같은 원본의 구간을 train/test에 나누지 않는다.
분할만으로 모든 문제가 해결되는 것은 아니다.

## 4. 카메라 등록·ROI·실행 전 점검

`/sessions`에서 장소와 세션을 만들고 카메라별 파일을 연결한다. 촬영 시각이 미확인이면 independent/planned로 구분한다.
실제 3대 카메라의 독립 시야와 같은 시간 촬영 여부는 영상으로 검증한다. 같은 파일 3개로 실제 다중 카메라 검증을 대신하지 않는다.
각 원본 해상도에 맞는 ROI를 등록·확인하고, 실제 분석에 사용하도록 승인한 뒤 작업을 요청한다.
다른 영상의 ROI/중앙 방향 경계/시계 검증을 자동 복사하지 않는다.

신규 분석 요청은 DB 큐에 등록되며 한 영상의 queued/running 중복 요청은 409이다.
카메라 3대는 서로 다른 영상의 작업 3개로 등록하고 **순차 처리**한다.
`Worker.exclusive`의 로컬 lock과 DB advisory lock이 있어 GPU가 여럿이어도 현재 구현은 동시에 여러 Worker를 실행하는 설계가 아니다.

현재 GPU는 GTX 1060 3GB 1대이다. 기존 GPU 환경은 torch 2.5.1+cu118로 CUDA 사용 가능/SM61 지원을 확인했다.
드라이버에 CUDA 12.6이 표시된다고 CPU용 Python이 GPU 추론을 할 수 있는 것은 아니다.
기존 GPU 환경의 인터프리터를 사용하고, 승인된 기존 로컬 모델/해상도를 유지한다. 자동 다운로드/자동 CPU fallback은 없다.
기존 단기 검증은 YOLO11n/960/FP32이다. 기본값 yolo11m/1920의 VRAM 적합성은 별도 canary가 필요하다.

이미 Worker가 돌고 있으면 두 번째 Worker를 띄우거나 기존 것을 종료하지 않는다.
기존 Worker가 없고 설정이 확인됐을 때만 담당자가 범위를 제한하여 실행한다:

```powershell
& <기존GPU_Python> -B -m app.worker --model-path <기존로컬모델> `
  --algorithm-version <승인된버전> --device cuda:0 --imgsz <승인된크기> `
  --flow-method full_frame --once --job-id <확인한작업UUID>
```

작업 디렉터리는 backend이다. 위 값은 실제 확인한 값으로 채운다. 이번 점검에서 새 Vision Worker/모델 추론을 시작하지 않았다.
먼저 짧은 실제 구간으로 ROI·FPS·VRAM·RAM·단계별 시간과 저장 행 수를 확인한다.
원본의 고밀도 구간도 점검하여 최초 한 구간의 평균만으로 전체 규모를 추정하지 않는다.

## 5. 진행률·실패·재시도

업로드 진행률은 전송 비율이다. 분석 퍼센트/ETA가 아니다.
분석 API는 queued/running/succeeded/failed 상태를 제공하며 화면은 진행 작업을 약 5초 주기로 조회한다.
프레임별 분석 퍼센트·정확한 남은 시간·카메라별 병렬 스케줄러는 구현되어 있지 않다.
`worker.log`, `execution_metadata.json`, `analysis_details.json`, CSV와 API 결과 상태를 함께 확인한다.

실패는 기존 작업을 덮어쓰지 않고 새 작업으로 재시도한다. 자동 재시도/자동 전체 영상 재실행은 없다.
CUDA OOM이면 명확한 실패를 남기고 해당 Worker 루프가 종료되어 나머지 작업은 대기할 수 있다.
설정 원인을 확인하기 전에 반복 재시도하지 않는다. 이번 점검에서 기존 Worker를 종료한 적은 없다.
중단 작업 복구는 Worker token/lock을 확인한 뒤 이전 running을 failed로 표시하는 기존 로직을 사용한다.
진행 중 작업의 시간 제한/취소 UI를 새로 추가하지 않았다.

## 6. 결과 검수·재생

성공 상태뿐 아니라 실제 전체 프레임 decode, 해상도/FPS, 원본/ROI hash, 요청/실제 device, model/version을 확인한다.
원본 영상의 시작/중간/끝을 재생하고 원본 시각과 2D/3D·공통 시간축을 대조한다.
HTTP Range 성공은 codec 재생 성공이나 대규모 2D/3D 성능 보장이 아니다.
큰 replay는 현재 전체 JSON/배열로 로드하며 cache도 유지한다. 1시간 다중 카메라 관제 UI의 메모리/장시간 성능은 추가 검증 대상이다.
누락/저신뢰/미동기화를 정상 또는 0명으로 바꾸지 않는다.

## 7. Forecast 담당자 전달

검수한 실제 세션에서 1초 간격 CSV를 우선 추출하고 필요하면 5/10/30/60초도 전달한다.
카메라별·구역별 필터로 출력 규모를 제한한다. CSV는 long-format이며 여러 카메라를 자동 합산한 정답이 아니다.
현재 세션 export는 카메라/영상에 연결한 **단일 roi_name**만 읽는다. 원본 분석의 모든 ROI를 자동 출력하지 않는다.
모든 ROI가 필요하면 기존 결과 화면의 원본 CSV 링크로 함께 전달한다. 물리 카메라를 가짜 ID로 복제하여 우회하지 않는다.
완료 분석이 연결되지 않은 카메라는 export에서 빠질 수 있다. HTTP 200/헤더만 있는 CSV를 학습 데이터 준비 완료로 보지 말고 행 수를 확인한다.
함께 전달할 파일:

- 실제 관측 CSV와 `/api/capture/schema` JSON (capture-long-v1, 31컬럼)
- session_id/revision, venue_id/revision, camera_id, video/job ID, ROI 이름과 목표 구역 ID
- 촬영 시각·시간대·오프셋·검증 근거, 이벤트/달력/조명/환경, 미확인 항목 목록
- 원본/모델/결과 fingerprint 및 hash, 해상도/FPS/프레임 수, device/profile/Flow 정책
- 원본 ROI/지도/통로 보정, 시야 중복·관측 누락·저신뢰 구간
- 원본 recording group과 카메라 동시 촬영 그룹, 학습/검증/테스트 분할 계획
- 정답을 확보했다면 별도 미래 인원/유입/유출 annotation과 horizon 정의

timestamp는 검증된 촬영 시각이 있을 때 완료 구간 끝이다. 미확인은 null이다.
count_change/rolling_mean은 과거 완료 구간만 사용하며 세션 간 상태를 공유하지 않는다.
실제 학습 split을 자동 강제하지는 않으므로 담당자가 원본/날짜/동시 촬영 그룹을 먼저 분리한다.
누락 값은 빈 셀이고 0 대체/미래 보간을 하지 않는다. 방향/역방향 및 사후 병목 특징의 null을 임의로 채우지 않는다.
모델 입력용 미래 정답은 현재 export에 자동 포함되지 않는다.

기존 `video_pipeline`은 별도 규격이며 실행 중 학습과 보간/0 채움이 있다.
[Forecast 실행 안내](FORECAST_RUNTIME.md)의 변환/누수 주의를 확인한다. 이번 점검에서는 학습/재학습하지 않았다.
서울 행정동 1시간 생활인구 모델과 영상 기반 단기 집중 추정을 혼합하지 않는다.

## 8. Isolation Forest와 SHAP

`forecast/anomaly_video.py:iforest_scores`에 IsolationForest 구현이 있다.
`video_pipeline.run_video_forecast`가 motion 완전성과 구역당 유효 10초 sliding 창 30개 조건에서 이를 호출한다.
실행 시 전체 입력의 통계와 `.fit`을 사용하고 전체 score를 0~1로 정규화한다. 고정 사전 학습 아티팩트가 아니며 사후 이상 탐지이다.
미래 사고 확률/보정된 위험 점수로 해석하거나 시간순 평가에 그대로 사용하지 않는다.
현재 운영 API/관제 UI와 실제 연결되어 있지 않다. 제한사항에 따라 이번 점검에서도 실행하지 않았다.

SHAP import/Explainer/`pred_contrib`/시각화·API 연동은 프로젝트 실행 코드에서 찾지 못했다.
CPU/GPU/Forecast 세 환경에도 shap 패키지가 없다. 단순히 LightGBM이 있다는 이유로 SHAP 구현 완료로 보지 않는다.
설치나 신규 설명 기능 추가는 하지 않았다.
